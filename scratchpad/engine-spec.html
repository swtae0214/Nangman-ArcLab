§1 인증 프로토콜

apps/api/src/common/guards/anonymous-session.guard.ts

회원가입/로그인 없이 "내가 만든 것"만 구분하기 위한 익명 세션 방식입니다. 토큰 두 개가 서로 다른 일을 합니다.

토큰저장 위치용도노출 범위
owner_token httpOnly 쿠키 (1년) 수정/삭제 등 모든 쓰기 작업의 소유권 판별 절대 URL에 노출 안 됨, JS로 못 읽음
share_token URL 경로 공개 읽기 전용 링크 URL만 있으면 누구나 열람 (수정 불가)

요청이 들어왔을 때 벌어지는 일

  1. AnonymousSessionGuard가 요청의 owner_token 쿠키를 확인한다
  2. 쿠키가 없으면 randomUUID()로 새로 발급해 httpOnly 쿠키로 내려준다
  3. 쓰기 요청(POST/PATCH/DELETE)은 저장된 리소스의 소유자 토큰과 일치해야만 통과한다
  4. 읽기 요청(GET)은 소유자이거나, 리소스가 isPublic=true면 통과한다
  5. /shared/:shareToken은 이 가드를 아예 안 걸어서, 쿠키 없는 익명 방문자도 접근 가능하다

두 세션(예: 서로 다른 브라우저)은 서로 다른 owner_token을 가지므로, 한쪽에서 만든 비공개 아키텍처를 다른 쪽이 직접 수정할 방법은 없습니다 — 공유 링크로 열람만 가능합니다.

§3 SPOF 탐지 알고리즘

apps/api/src/modules/validation/{graph.util,rules/spof.rule}.ts

"이 컴포넌트 하나가 죽으면 로드밸런서에서 DB로 가는 길이 완전히 끊기는가"를 그래프 이론으로 판정합니다. 두 단계로 나뉩니다.

1단계 — 절단점(articulation point) 탐색: Tarjan's Algorithm

DFS 한 번으로 전체 그래프의 절단점을 찾습니다. 두 값을 씁니다.

discovery[u]
u를 처음 방문한 순번
low[u]
u에서 역방향 간선을 타고 되돌아갈 수 있는 가장 이른 조상의 순번
절단점 판정 조건
low[v] ≥ discovery[u] → u는 절단점 (단, u가 루트면 자식이 2개 이상일 때만)

자식 v가 u의 discovery 시점보다 더 이른 조상으로 못 돌아간다면, v 쪽 부분 그래프는 u를 거치지 않고는 나머지와 못 이어진다는 뜻입니다.

2단계 — 검증과 무관한 절단점 걸러내기

그래프의 절단점이라고 전부 SPOF는 아닙니다(예: 독립된 CDN 곁가지). 절단점 각각을 제거해보고, 그래도 어느 로드밸런서에서 어느 DB로도 못 가는 경우만 SPOF-001 위반으로 남깁니다.

최종 필터
SPOF = { p ∈ 절단점들 | ∄ lb ∈ LB : reachable(lb, DB들, exclude=p) }

§4 M/M/c 큐잉 모델 (Erlang C)

apps/api/src/modules/simulation/queueing.util.ts

노드 하나(웹 서버 계층, 캐시, DB)를 대기열이 있는 창구 c개짜리 서비스로 보고 지연시간과 처리량을 계산합니다. 켄달 표기법 M/M/c — 도착도 서비스도 지수분포(Markov), 서버는 c대.

λ (lambda)
도착률 — 초당 들어오는 요청 수
μ (mu)
서버 1대의 처리율 — 초당 처리 가능 요청 수
c
서버(인스턴스) 대수

1. 이용률

a = λ／μ　　　ρ = a／c

ρ ≥ 1이면 처리 능력을 넘어선 포화 상태로 바로 처리합니다 — 아래 공식의 (1−ρ) 항이 0 이하가 되어 발산하기 때문입니다. 이때 처리량은 c·μ로 잘립니다.

2. 대기 확률 (Erlang C)

P0 — 시스템이 비어있을 확률
P0 = [ Σn=0…c−1 aⁿ／n!　+　ac／(c!(1−ρ)) ]−1
C(c,a) — 도착한 요청이 대기해야 할 확률
C(c,a) = [ ac／(c!(1−ρ)) ] · P0

3. 대기·지연시간

Lq = C(c,a) · ρ／(1−ρ)　　（평균 대기 행렬 길이）
Wq = Lq／λ　　（평균 대기시간）
W  = Wq + 1／μ　　（평균 종단 지연시간 = 대기 + 서비스）

웹 서버가 Auto Scaling Group으로 묶여 있으면(9단계부터는 물리적 소속이 아니라 논리적 logicalGroupId 기준) 같은 그룹의 인스턴스 수를 그대로 c에 대입해 하나의 큐로 합칩니다.

§5 가용성 추정 공식

apps/api/src/modules/simulation/availability.util.ts

관찰 기간 동안 "장애 구간엔 장애 중 처리량으로, 나머지엔 평상시 처리량으로 돌아갔다"고 보고 시간 가중평균을 냅니다. 처리량이 요청량에 못 미친 비율만큼 가용성이 깎인다는 단순화된 모델입니다.

단계 1 — 구간별 처리율
f(x) = min(1,  throughputx ／ expectedRps)
단계 2 — 시간 가중평균
availability(%) = (T_obs − T_fail)·f_base + T_fail·f_failT_obs × 100
T_obs
관찰 기간 (observationPeriodSec)
T_fail
장애 지속 시간 — 관찰 기간을 넘지 않게 clamp됨
f_base / f_fail
평상시 / 장애 중 처리율 (§4의 throughputRps에서 유도)

§6 장애 주입 모델

apps/api/src/modules/simulation/failure-scenario.util.ts

failure_scenarios.affects_rule 하나가 두 가지 방식 중 하나로 그래프를 바꿉니다.

방식동작예
removeNodeTypes 해당 타입 노드를 그래프에서 통째로 제거 (연결된 엣지도 함께) DB Primary 장애
capacityReductionRatio + scope scope 그룹의 자손 노드 인스턴스 수를 비율만큼 축소 AZ 하나 다운 → 인스턴스 절반 상실

노드가 "어느 물리적 AZ에 있는지"까지는 모델링하지 않으므로(Multi-AZ 그룹은 "여러 AZ에 걸쳐 있다"는 사실만 표현), "AZ 하나 다운"은 정확한 절반이 아니라 근사치로 다룹니다 — 설계 문서에서도 밝힌 한계입니다.

구간별 병목(처리량) 계산

여러 구간의 throughput을 그냥 min()으로 비교하면 틀립니다 — 캐시가 흡수해서 자연히 λ가 작아진 구간이 포화되지도 않았는데 병목으로 잘못 뽑히기 때문입니다.

throughput_전체 = 포화 구간이 없으면 expectedRps, 있으면 min(포화 구간들의 throughput)
